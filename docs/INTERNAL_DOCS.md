# PRANTE / ПРАНТЕ — внутренняя документация

Статус: рабочий внутренний SSOT.  
Назначение: быстро сориентировать команду, где лежит продуктовая, исследовательская и техническая документация проекта.

## 1. Что такое ПРАНТЕ

**ПРАНТЕ** — Telegram-first ассистент для письменного переводчика. Он автоматизирует предпереводческий анализ текста и постепенно формирует персональный переводческий профиль пользователя: глоссарий, переводческую память, правила проекта/жанра/клиента и стилевые предпочтения.

Короткая формулировка:

> ПРАНТЕ помогает переводчику быстрее подготовиться к переводу, контролировать терминологию и постепенно снижать количество повторяющихся правок за счет адаптивной памяти.

## 4. Консолидированное видение продукта

ПРАНТЕ развивается в три слоя.

### Слой 1. Предпереводческий анализ

Функции:

- подсчет повторов;
- частотные фразы;
- кандидаты в термины;
- первичная оценка структуры текста;
- экспорт отчета.

Ценность: переводчик быстрее понимает, с чем имеет дело до начала перевода.

### Слой 2. Глоссарий и контроль терминологии

Функции:

- личный/проектный глоссарий;
- preferred translations;
- forbidden variants;
- подсветка терминов в исходнике;
- проверка сохранения терминологии в переводе;
- предложения новых терминов.

Ценность: меньше терминологических ошибок и ручной проверки.

### Слой 3. Адаптивная переводческая память

Функции:

- сохранение пар source → final translation;
- сравнение LLM/MT-черновика с финальной версией;
- сравнение финальной версии с одобренной заказчиком;
- извлечение устойчивых правок;
- предложение новых правил;
- scoped rules для пользователя, проекта, клиента, жанра;
- использование правил в следующих переводах.

Ценность: ПРАНТЕ постепенно адаптируется к стилю переводчика и требованиям заказчика без непрозрачного fine-tuning.

## 5. Архитектурный принцип

Не строить ядро продукта как полностью автономного агента.

Правильная схема:

```text
Детерминированные tools + управляемая LLM + память с подтверждением пользователя
```

Детерминированно:

- повторы;
- поиск терминов;
- fuzzy matching;
- сравнение версий;
- подсчет метрик;
- проверка чисел, дат, именованных сущностей;
- хранение глоссария и правил.

LLM используется для:

- чернового перевода;
- объяснения правок;
- предложения формулировки правила;
- стилистической диагностики;
- ранжирования терминов-кандидатов.

Пользователь подтверждает:

- добавление термина;
- запрет варианта;
- правило проекта/жанра;
- переводческую память;
- применение правила глобально.

## 6. Backend stack — текущая рекомендация

### MVP backend

- Python.
- FastAPI для API.
- aiogram для Telegram bot.
- SQLite на раннем этапе, Postgres при командной работе/деплое.
- RapidFuzz для fuzzy matching.
- pyahocorasick или FlashText для glossary exact matching.
- spaCy/Stanza для сегментации и NLP.
- YAKE/PyTextRank для терминов-кандидатов.
- textstat + собственные метрики для читабельности.
- LLM provider abstraction для чернового перевода.

### После MVP

- Qdrant для semantic translation memory.
- COMET/sacreBLEU для offline evaluation.
- Vercel AI SDK / assistant-ui для web UI.
- CopilotKit + AG-UI, если нужен богатый agent UI с событиями tools/state.

## 7. Product roadmap

### Phase 1 — исследовательский MVP

Цель: показать ценность предпереводческого анализа.

- Telegram bot принимает текст.
- Считает повторы.
- Извлекает кандидаты в термины.
- Позволяет добавить термин в глоссарий.
- Экспортирует отчет.

### Phase 2 — глоссарий и QA

Цель: доказать пользу терминологического контроля.

- CRUD глоссария.
- Exact/fuzzy терминологический matching.
- Проверка перевода на preferred/forbidden terms.
- Inline-кнопки: “запомнить”, “запретить”, “не сейчас”.

### Phase 3 — draft/final learning loop

Цель: начать адаптацию к пользователю.

- Хранить source/draft/final.
- Сравнивать черновик и финал.
- Предлагать term/rule candidates.
- Approval loop.

### Phase 4 — project/client/genre rules

Цель: сделать ПРАНТЕ персональным переводческим профилем.

- Правила по scope: global/client/project/genre.
- Конфликты правил.
- Evidence для каждого правила.
- Подстановка правил в prompt.

### Phase 5 — web UI

Цель: дать визуальный интерфейс для сложной работы.

- Side-by-side source/draft/final.
- Подсветка правок.
- Queue подтверждения памяти.
- Панель глоссария и правил.
- Structured tool events.

## 8. Риски

### Загрязнение памяти

Риск: система начнет запоминать случайные правки как правила.

Защита:

- статусы candidate/user_approved/client_approved/active/deprecated;
- evidence для каждого правила;
- ручное подтверждение;
- scope по проекту/жанру/клиенту.

### Непрозрачность LLM

Риск: продукт станет “магическим чатом”, которому сложно доверять.

Защита:

- deterministic tools first;
- JSON tool outputs;
- объяснимые отчеты;
- не парсить свободный текст агента;
- показывать evidence.

### Слишком широкий MVP

Риск: команда попытается сделать CAT/TMS-комбайн.

Защита:

- MVP Telegram-first;
- 3–4 ключевых сценария;
- web UI и semantic memory — после подтверждения базовой ценности.
